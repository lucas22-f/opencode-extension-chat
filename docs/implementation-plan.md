# Implementation plan

The sequence below mirrors the authoritative M0–M10 milestone table in [`../odd/tasks/opencode-visual-extension.md`](../odd/tasks/opencode-visual-extension.md). That ODD document alone owns acceptance criteria, status, evidence, and next step; this file is a concise sequencing guide, not a second task tracker.

## Milestone sequence

1. **M0 — Research and architecture:** pin OpenCode 1.19.0, document source-level research and design constraints, define feature acceptance, and verify the isolated sparse reference clone at the pinned commit. Complete at research/reference level only; the nested upstream checkout is not product code and does not imply runtime verification.
2. **M1 — Minimal Extension Host + React Webview scaffold:** establish the distinct extension identity and sidebar/expanded Webview shell. The Windows managed path resolves the real PowerShell shim from PATH, derives and validates the adjacent `opencode.exe`, and spawns it directly with safe fixed argv, an explicit trusted-workspace cwd, reported URL, exact process ownership, graceful disposal, and bounded fallback cleanup. Cancellation after lease acquisition releases the lease before spawn; lease conflicts remain actionable. Extension Host/coexistence checks remain pending.
3. **M2 — Real OpenCode connection/server health:** use the pinned `@opencode-ai/sdk@1.19.0` health route with an explicit attach-only URL or one default `127.0.0.1:4096` probe. A no-response result may start a trusted-workspace managed server on loopback with port `0` and `--pure`. The user-run health-only managed smoke passed its loopback, `/global/health` 1.19.0, owned-process-stop, endpoint-unavailable, and empty-lease assertions. It reported `SMOKE_SHUTDOWN=owned-tree-fallback`: graceful SDK disposal did not stop the process within the grace window, and bounded fallback forcibly terminated only the owned process tree, so graceful shutdown remains unverified. Earlier cancelled-smoke PIDs 20696 and 11100 were stopped only after explicit user authorization; unrelated PID 13256 was left untouched. Configured-URL live attach and VS Code Extension Host/coexistence checks remain pending.
4. **M3 — Real chat, sessions, and streaming:** connect prompt/session flow to the server and render responses incrementally from real pinned events. Do not simulate response streaming or session state.
5. **M4 — Tools:** derive tool cards, types, states, and supplied metadata from actual events. Show file changes only when verified payloads provide them.
6. **M5 — Permissions/questions:** display and respond to server-issued permission and question requests using verified pinned operations and server-refreshed state.
7. **M6 — History/models:** support server-returned history and open/resume/create; send delete only after confirmation and only if the pinned API supports it, otherwise document and omit it. Populate provider/model/agent choices only from server-returned values; `Agent.Info.mode` is classification, not a user-selectable mode.
8. **M7 — Editor files/context/diffs:** pass active-file, selection, and line-range references through VS Code APIs; gate attachments, change summaries, native diff/editor navigation on verified OpenCode and VS Code support.
9. **M8 — MCP/skills/subagents:** implement read-only MCP status, model-scoped experimental tool metadata, skill metadata, and child sessions derived from exact server-returned `parentID`; keep missing ownership/source-state/filter endpoints and unsupported administrative actions explicit.
10. **M9 — Security, reliability, tests, performance:** complete workspace-trust, credential, CSP/input, multi-window/workspace, Windows-path, cancellation, and recovery checks; add and run unit, integration, contract, Extension Host/UI, and real v1.19.0 checks. Record resource use as observations. Provider-cost E2E remains optional and explicitly authorized.
11. **M10 — Docs, VSIX, clean install, report:** deliver README and architecture/development/testing/troubleshooting/security/compatibility/changelog documentation; inspect VSIX metadata/content and confirm `upstream-opencode-v1.19.0/` is excluded; verify clean side-by-side installation where available; report exact evidence, known limitations, and artifact location.

## Verification and sequencing rules

- The first baseline remains OpenCode CLI/SDK 1.19.0. The SDK package root and `./v2` subpath are distinct surfaces; use each only for routes verified in the pinned version. OpenCode 2.x remains unsupported until a separate compatibility change is verified.
- Record exact pass/fail/blocked outcomes in the canonical ODD tracker. The product now has a pnpm toolchain, scripts, and focused tests; the nested source-reference clone is not product code. `vsce` was not found.
- Keep test workspaces isolated from user workspaces. Optional provider-cost E2E must be explicitly authorized before running. Do not invent performance or memory thresholds; record scenario and observed values until a baseline is agreed.
- Keep changes reviewable by coherent milestone. A roughly 400-line size is advisory only and must not force an artificial split.

## Current handoff

**M8 read-only inventory:** The Extension Host independently loads `GET /mcp`, experimental `GET /experimental/tool?provider=…&model=…`, experimental `GET /api/skill`, and bounded cursor pages of v2 `GET /api/session`. Tool metadata is requested only for a known server-returned provider/model and is labeled as server-default-agent scope, not necessarily the selected agent. Skill content and local locations are omitted. Child rows require exact returned `parentID === selectedSessionID`; “Subagent” requires the returned matching agent mode `subagent`. The UI has independent idle/loading/empty/unavailable/error states and load/refresh actions only. No MCP ownership mapping, separate enable endpoint, v2 parentID filter, skill source-state field, admin/invocation controls, or live runtime verification is claimed. M8 remains partial; mocked adapter/protocol/Webview tests only.

**M9 user-triggered interruption:** Session selection and event-stream reconnect read `client.v2.session.active()`; native `session.status` busy/retry events establish selected-session activity, and idle notifications reconcile with the active map. A stop control appears only for a known-active selected session and calls `client.v2.session.interrupt({sessionID})` only after a user click. HTTP 204 leaves the UI in “stop requested/waiting” until matching idle confirmation or a refreshed active map reports absence. Request failures preserve activity and expose retry. Focused mocked verification passed 117 tests across the adapter/protocol/Webview files; `pnpm run typecheck` and `pnpm run build` passed. No live cancellation outcome was tested, so M9 remains partial.

**M5 permission/question follow-up:** The pinned session list/reply/reject routes and v2 `permission.*` / `question.*` event shapes are implemented. Request IDs are taken from `data.id` on asks and `data.requestID` on replies, always paired with `sessionID`; pending state is refreshed from server lists and resolution events. Focused mocked transport/UI/protocol verification passed 71 tests across 3 files, and the production build passed. No live permission or question response was performed, so M5 remains partial.

**Late-delta follow-up:** The 51-test four-file M3 run above predates this narrow correction. The latest `tests/opencode-chat.test.ts` run passed 17 tests after adding late-event handling for history-mapped parts. Pinned `AssistantText` history parts share `textID` but have no per-part timestamp; already-contained late chunks are suppressed, unmatched chunks are overlap-merged, and `text.ended` replaces partial text. The ambiguous history `haha` + late `ha` case remains `haha` until the final event supplies `hahaha`; absent that event the ambiguity remains unresolved. Typecheck/build passed; no live server or session data was used.

**M6 session-history follow-up:** Session search/list pagination uses `/api/session` server cursors, and older message pages use `/api/session/:sessionID/message` cursors while preserving server order and deduplicating. Provider/model/agent choices are loaded only from location-scoped server data; experimental provider/model discovery failures are surfaced as unavailable rather than replaced with local guesses. Model/agent selections use the supported create and v2 switch routes. Deletion calls only the SDK root legacy session route after a native modal where Cancel is first and marked as the close/Escape action. Focused mocked transport/UI/protocol verification passed 90 tests across three files; `pnpm run build` passed. M6 remains partial pending live v1.19.0 verification; no live session, choice, switch, or delete request was made.
