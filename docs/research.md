# OpenCode and VS Code research

## Executive finding

The inspected OpenCode v1.19.0 VS Code extension is a terminal launcher/context bridge, while the requested product is a separate chat-first UI. Use an independent extension identity and pin the initial compatibility target to OpenCode 1.19.0. Treat current OpenCode 2.x docs and source as version drift, not as a verified contract for the installed CLI.

The M0 entries below record static research and the parent-verified local reference checkout. The M2 addendum records the installed SDK, managed-server implementation, and user-run health-only managed smoke, which required the owned-tree fallback; graceful shutdown remains unverified. The M3, M5, M6, M7, M8, and M9 addenda record pinned routes, capability boundaries, and deterministic mocked verification. No real OpenCode prompt, session mutation, permission response, question response, M8 capability request, or cancellation outcome has been tested. The checkout is official OpenCode source for inspection only; it is not product code or a fork.

## First-prompt session topic titles

The extension uses the pinned public legacy `PATCH /session/:sessionID` (`session.update`, directory-scoped, title-only payload) after a validated v2 prompt admission. It rechecks v2 session metadata before changing an untouched default root title. The title is an 80-code-point excerpt of the first nonblank prompt line, not an additional model call. Custom titles, existing user history, child titles, incomplete history and rejected/uncertain admissions do not trigger naming. Only a confirmed matching response updates the UI; failures preserve prompt acceptance without automatic retry.

Persistence evidence at [`733b2c`](https://github.com/anomalyco/opencode/tree/733b2c627e5aec39cb33cc22373bdce33053ef2c): `packages/opencode/src/server/routes/instance/httpapi/groups/session.ts` declares the update route; its handler calls `session.setTitle`; `packages/opencode/src/session/session.ts` publishes `SessionV1.Event.Updated`; `packages/core/src/session/projector.ts:234-239` updates the same `SessionTable` read by v2 session metadata/listing. Legacy `SessionPrompt.ensureTitle` is not evidence that the newer core runner generates titles. The API offers no compare-and-swap: an external rename during GET/PATCH can still race; no atomic preservation guarantee is claimed. Verification uses isolated mock HTTP state, not the user's sessions.

## M3 session and text-event contract

The implementation uses the exact installed `@opencode-ai/sdk@1.19.0` package through the package's `@opencode-ai/sdk/v2/client` export. The generated SDK keeps the `v2` route family under `client.v2`; top-level `client.session` and `client.event` are legacy endpoints and are not used for M3. This distinction is material: legacy event objects use `properties`, while the v2 event stream uses `data`.

| Operation | SDK method | Pinned route and payload |
|---|---|---|
| List sessions | `client.v2.session.list` | `GET /api/session`; workspace location and bounded page size are selected by the Extension Host. |
| Create session | `client.v2.session.create` | `POST /api/session`; body `{ location: { directory } }`, with the directory sourced from the VS Code workspace, never the Webview. |
| Load messages | `client.v2.session.messages` | `GET /api/session/:sessionID/message`; recent page requested with `limit` and `order`. The UI displays returned user and assistant text only. |
| Submit prompt | `client.v2.session.prompt` | `POST /api/session/:sessionID/prompt`; body `{ id: "msg_<stable Webview UUID>", prompt: { text }, delivery: "steer" }`. Success acknowledges durable admission; it is not an assistant response. |
| Subscribe to live events | `client.v2.event.subscribe` | `GET /api/event`; native v2 SSE stream. The Extension Host filters by selected `sessionID`. |

`packages/protocol/src/groups/session.ts` defines list/create/prompt and per-session event routes; `packages/protocol/src/groups/message.ts` defines the v2 message history route. The generated SDK types in `packages/sdk/js/src/v2/gen/{sdk.gen,types.gen}.ts` provide the `SessionV2Info`, `SessionMessage`, `SessionInputAdmitted`, and `V2Event` contracts. The `/api/event` handler in `packages/server/src/handlers/event.ts` sends `server.connected` with `{id,type,data}` after installing the event listener, which provides a real readiness boundary before prompt submission.

The v2 prompt body accepts optional `id?: SessionMessage.ID`. `packages/schema/src/session-message.ts` requires this ID to begin with `msg_`; the Webview retains a stable request UUID and the Extension Host maps it deterministically to `msg_${requestID}` for the server. Each user send/retry also has a fresh `attemptID` used only to correlate the Webview result, preventing a previous outcome-unknown result from completing a newer attempt. `packages/server/src/handlers/session.ts` forwards the ID to `SessionV2.prompt` and maps `Session.PromptConflictError` to HTTP 409. The pinned core implementation confirms exact durable-admission idempotency: `SessionInput.admit` returns an existing inbox row by ID, and `SessionV2.prompt` accepts it only when session, canonical prompt, and delivery match; a mismatch raises a conflict. The pinned `packages/core/test/session-prompt.test.ts` covers exact and concurrent retries returning one recorded admission and conflicting prompt/delivery/session reuse. Omitting the ID creates a distinct message. Each call may still request execution wake unless `resume: false`, so this is a durable-admission guarantee, not an exactly-once provider-execution guarantee. M3 exposes an explicit retry using the same derived server ID only while session and prompt text are unchanged; it never automatically retries. The core source is not materialized in the local sparse checkout; these findings were checked against raw source and tests at the pinned commit, not floating documentation. `SessionInputAdmitted` returns an `id`, `sessionID`, prompt, delivery, admission sequence, and time; `session.next.prompt.admitted` carries a `messageID` and prompt.

The supported assistant text deltas are `session.next.text.delta` with `data.timestamp`, `data.sessionID`, `data.assistantMessageID`, `data.textID`, and `data.delta`; `session.next.text.ended` carries the final text for the same session/message/text-part identity. `SessionMessage.AssistantText` history parts expose `id` and `text`, but no part timestamp or delta sequence. The projected assistant message has `time.created` and optional `time.completed`, which do not identify an individual text delta's ordering against the history snapshot. The v1.19.0 `SessionMessageUpdater` creates/looks up the text part by `event.data.textID`, appends delta text, and replaces the part value on `Text.Ended`; the message handler returns those projected `SessionMessage.Message` records. This confirms part-ID equality, but not timestamp comparability for history-mapped text.

M3 deduplicates by event ID, ignores events for other sessions, maintains text per assistant message and part ID, rejects strictly older timestamps for event-derived parts, and processes equal-timestamp fragments in SSE arrival order. M3 does not synthesize tool or reasoning states; the M9 cancellation control is grounded separately in the pinned active-session and status contracts below.

The session-specific `/api/session/:sessionID/event` stream replays durable session events, but its pinned `SessionDurableEvent` union excludes `session.next.text.delta`. It therefore cannot supply incremental text. Native `/api/event` has no replay cursor for these transient deltas: the server leaves the SSE frame ID unset, and the SDK's `Last-Event-ID` handling only applies when that frame field is present. M3 establishes the native listener and waits for `server.connected` before requesting history, buffers text events during the snapshot, and reloads projected history after `server.connected` on SDK reconnection. For a late delta targeting a history-mapped part (matching `textID`/part `id` but no event timestamp), it ignores a delta already contained in the current part value and otherwise merges text overlap before updating the visible message. A `session.next.text.ended` event replaces the part with its replayable full value. This prevents verbatim duplicate chunks while preserving genuinely new suffixes. For example, when history contains `haha` and a genuinely new late `ha` arrives, the client conservatively leaves the displayed text as `haha`; if the ended event arrives, it replaces the text with authoritative `hahaha`. If `text.ended` is absent, no v1.19.0 part revision/sequence/timestamp can resolve whether that repeated fragment was already represented. Overlap reconciliation remains ambiguous, and events before the listener is installed cannot be replayed. The implementation does not claim lossless recovery across those protocol limits.

The Extension Host initializes the session client only when the workspace is trusted and supplies the workspace directory; the Webview cannot choose paths. M3 loads the latest 100 messages. M6 adds server search and cursor pagination for session lists and message history; session pages preserve server order, and older message pages are merged before loaded messages without duplicate IDs. The active session remains separately visible when outside the loaded page or search results. Copy-code messages contain only extracted rendered code text and use the VS Code clipboard API. Known prompt API 4xx rejection preserves the draft; network/unknown failures are surfaced as outcome-unknown and retain it. The UI never retries prompts automatically. A user can explicitly retry only the unchanged text in the same session, reusing the same `msg_` server ID and generating a fresh attempt-correlation UUID; OpenCode v1.19.0 returns the original admission for the exact session/prompt/delivery tuple and conflicts on mismatched reuse. Drafts clear only after a validated accepted-admission response for the current attempt. M3/M6, M8, and M9 transport verification uses deterministic fake HTTP/SSE only. No real prompt, provider call, session mutation/deletion, M8 capability request, or cancellation outcome was performed. Syntax highlighting, M4 tool cards, live cancellation behavior, and live runtime verification for M3/M6/M7/M8/M9 remain pending or out of scope for those milestones; M8's mocked capability inventory is documented below.

## M5 permission and question contract

The M5 implementation uses only the pinned `@opencode-ai/sdk@1.19.0` v2 session routes and native `/api/event` events. It does not interpret legacy `properties` envelopes.

| Operation | Pinned route / event | Contract |
|---|---|---|
| List pending permissions | `GET /api/session/:sessionID/permission` | Returns `{ data: PermissionV2Request[] }`, scoped to the session. |
| Reply to permission | `POST /api/session/:sessionID/permission/:requestID/reply` | JSON `{ reply: "once" | "always" | "reject", message?: string }`; response is `204 No Content`. The UI exposes the three supported reply values and does not send an optional message. |
| List pending questions | `GET /api/session/:sessionID/question` | Returns `{ data: QuestionV2Request[] }`, scoped to the session. |
| Answer question | `POST /api/session/:sessionID/question/:requestID/reply` | JSON `{ answers: string[][] }`, preserving question order and each answer's selected labels; response is `204 No Content`. |
| Reject question | `POST /api/session/:sessionID/question/:requestID/reject` | No request body; response is `204 No Content`. |
| Permission request lifecycle | `permission.v2.asked`, `permission.v2.replied` | Ask payload is under `data` and carries `data.id` as request ID. Reply payload carries `data.sessionID` and `data.requestID`. |
| Question request lifecycle | `question.v2.asked`, `question.v2.replied`, `question.v2.rejected` | Ask payload is under `data` and carries `data.id` as request ID. Reply/reject payload carries `data.sessionID` and `data.requestID`. |

The native event envelope is `{ id, type, data }`: the outer `id` is an event ID, not the permission/question request ID. The Extension Host uses the outer ID only for event deduplication and correlates request lifecycle changes with the composite `sessionID + requestID` key. `permission.v2.asked` includes `action`, `resources`, and optional `save`, `metadata`, and `source`; `question.v2.asked` includes `questions` and optional `tool`. Only these server-supplied fields are displayed.

The client loads both pending lists after the event stream is ready, reloads them after reconnect, and buffers request lifecycle events while a list snapshot is in flight. After a successful reply route it refreshes both lists; the Webview does not optimistically remove a request. A request is removed when a matching resolution event or refreshed server list confirms it is no longer pending. Tests use deterministic mocked HTTP/SSE transport and verify routes, bodies, session/request correlation, snapshot races, message validation, and request controls. Focused result: 3 files / 71 tests passed; `pnpm run build` passed. No live permission or question request was answered or rejected.

## M7 editor context and text-only prompt use

The pinned v1.19.0 generated v2 SDK defines `PromptInput` with required `text` and optional `files` and `agents`. The v2 `POST /api/session/:sessionID/prompt` payload accepts that prompt object. The extension intentionally sends only `{ prompt: { text } }`; it does not use `PromptInput.files`, legacy `parts`, or an upload affordance. The presence of a file field in the type does not establish URI resolution or attachment processing on external/remote OpenCode servers.

The composer’s explicit Add editor context action and `opencodeVisual.addEditorContext` command capture `window.activeTextEditor` in the Extension Host. `OpenCodeConnection.connect` snapshots the `ConnectionWorkspace.directory` argument before awaiting health/startup and publishes that exact directory only when the supported connection succeeds. `OpenCodeChat` creates its client from that published snapshot; it does not sample the current first workspace folder after the await. The context action requires the captured root to remain the active first workspace folder. After asynchronous realpath validation, it re-reads `workspaceFolders` and `activeTextEditor` and rejects if the root/order/editor changed during validation. This closes both pending-connect and context-capture races without refreshing or switching the client. Capture also requires `workspace.isTrusted`, a `file:` document, and canonical containment. If the connected root is no longer the active workspace, or the editor is outside it or owned by a different workspace folder, capture fails with a visible message. `TextDocument.getText(selection)` supplies selected buffer text, including unsaved edits; no selection means a relative path reference only and no document text read. Selected text is bounded at 8,000 characters and the complete visible context block at 10,000; oversized values are rejected without truncation. The visible block states that relative paths are reference hints which a remote server may not be able to read. It is inserted into the editable draft, so it is part of exact prompt retry text; no hidden payload or session side channel is used.

The VS Code 1.138 `workspace.fs` interface has no realpath method. ## Server startup, health, and discovery

- In the pinned SDK, `createOpencode` starts an `opencode serve` child and returns the client and server handle. The helper defaults to host `127.0.0.1` and port `4096`, parses the actual listening URL from output, and supports closing the launched server. It is not used because it hardcodes the executable, inherits cwd, cannot supply `--pure` or the required arguments, and its close path does not await process exit.
- The pinned server tries port 4096 before falling back to port 0. The actual URL must therefore come from startup output rather than a hardcoded port.
- `createOpencodeTui` is a different helper that inherits stdio. The server process helper and process-stop/abort bindings are in `packages/sdk/js/src/server.ts` and `packages/sdk/js/src/process.ts`.
- The convenience `createOpencode` helper hardcodes the executable name `opencode`, inherits the parent cwd, and does not expose executable-path or cwd options. The read-only inspected Windows `.ps1` shim invokes `"$basedir/node_modules/opencode-ai/bin/opencode.exe"` directly and forwards `$args`. The manager now realpaths the shim found on PATH, derives and validates that adjacent executable, and spawns the executable directly; no PowerShell child is used for managed startup.
- The pinned `packages/opencode/package.json` is version `1.19.0` and declares its package bin as `./bin/opencode`. The installed Windows shim layout observed on this host resolves the packaged `opencode-ai/bin/opencode.exe` separately; runtime version compatibility is still checked through `/global/health` after startup.
- Direct `opencode serve --help` reports hostname default `127.0.0.1` and port default `0`. This CLI help default and the SDK helper's port 4096 default are different configuration layers, not contradictory runtime observations.
- `packages/opencode/src/cli/cmd/serve.ts` logs `opencode server listening on http://<hostname>:<actual-port>`; `packages/opencode/src/server/server.ts` owns port fallback behavior.
- `/global/health` returns health and version. `/api/health` returns only `{ healthy: true }`; use the version-bearing route when a version check is required.
- There is no typed route for discovering arbitrary existing TUI/server processes. Optional `--mdns` is DNS-SD, not a process-discovery API, and can affect bind behavior. On an explicit Connect action, the extension attaches to a configured URL without ownership, or probes only `127.0.0.1:4096`. It starts a managed server only if that probe receives no HTTP response; a responding non-OpenCode endpoint, timeout, auth challenge, or version mismatch does not trigger startup. No port/process scan occurs.
